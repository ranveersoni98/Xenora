### Added
- An original C++ guest fixture exercises compiler-generated Itanium ABI guard abort when a function-local constructor throws. A guest worker retries and initializes the object once, and startup controls require the three guard imports. The compiled fixture passes locally at two optimization levels on Apple Silicon (#1277).
- Added an original Microsoft x64 C++ package fixture that checks compiler-emitted global initialization in dependency order and per-DLL exit callbacks in reverse registration order (#1276). The EXE and two DLLs record their execution order in the synthetic guest drive.
- Added an original Microsoft x64 C++ ABI package fixture that constructs an object in one DLL, invokes and deletes it through a base pointer in another, and checks destructor order and heap release. A rejected handoff leaves the object live for a retry (#1263).
- The XAsync provider protocol core in `xgameruntime.dll` (#1252): `XAsyncBegin`, `XAsyncSchedule`, `XAsyncComplete`, `XAsyncGetStatus`, `XAsyncCancel`, `XAsyncGetResult` and `XAsyncGetResultSize`, plus the `XTaskQueueGetCurrentProcessTaskQueue`/`XTaskQueueSetCurrentProcessTaskQueue` pair the queue-less blocks fall back to. `XAsyncBegin` invokes the provider synchronously with `Begin` through the callback-task machinery; `XAsyncSchedule` queues the `DoWork` invocation on the work port and `XAsyncComplete` queues the caller's completion callback on the completion port, both riding a new exact-arguments form of queue callback since the protocol invokes providers with an operation code and data pointer rather than a context. The provider data block lives in the documented 32-byte `internal` space of the 56-byte `XAsyncBlock`. Retrieval honors the identity-mismatch `E_INVALIDARG`, the payload-less `E_NOT_SUPPORTED` and the size the completion recorded, and a successful retrieval chains the provider's `Cleanup` before the operation leaves the table. `XAsyncGetStatus` answers `E_PENDING` or the operation result with an optional blocking wait. Three original end-to-end fixtures compiled from C++ with native clang/LLD exercise the round trip, the cancel path and the process-queue fallback through the synthetic startup. Limitations: thread-pool queue modes cannot carry provider arguments yet and are refused with `ERROR_NOT_SUPPORTED`, operations never retrieved never run `Cleanup`, and the exact value of `E_NO_TASK_QUEUE` comes from independent public reconstructions rather than a Microsoft page. Local verification only.
- `WINHTTP_OPTION_CONTEXT_VALUE` in `WinHttpSetOption` and `WinHttpQueryOption`: the caller-owned opaque per-handle value Windows stores on every session, connection and request handle, zero until set, an eight-byte `DWORD_PTR` sized by the option contract, independent per handle and gone with the handle. Sized queries report the required eight bytes and the closed-handle query fails with the invalid-handle error. Local verification only.
- Native Metal compute commands can be packed into one bounded command buffer with `NativeCompute::submit_words_batch` and collected through `wait_batch` (#137). Each `(source, entry, input, output_slot)` tuple is checked before anything is encoded; up to eight commands share one completion wait, distinct output slots stay independent, reused slots share one output buffer, and one compute encoder carries every dispatch with a buffer-scope barrier following each dispatch but the last. Outputs are read after the whole batch completes, so commands that share a slot see its final contents. The in-flight table stays at sixteen submissions and reports a `queued_commands` bound of at most 128; invalid batches release every acquired buffer without inserting a submission. Original Apple M5 fixtures compare eight batched outputs with individual dispatches, exercise a shared-slot write/read pair across the barrier, and pin the empty, oversized, bad-slot and full-queue refusals. A pre-change probe of eight commands measured median host 3244.833 us and GPU 123.042 us across 20 samples; after the change, one manual comparison on the same host measured median host 2411.793 us for individual commands and 825.417 us for the batch, with GPU spans of 165.104 us and 159.208 us respectively. These are debug-build samples with warm pipelines on one device, not a general speedup, independent acceptance or game execution claim.
- `EncodePointer` and `DecodePointer` now resolve as partial `KERNEL32` services using a deterministic synthetic per-process cookie, with an original generated PE import test that round-trips a pointer through the translated service path. Windows does not publish a stable cookie algorithm, so no compatibility or cryptographic claim is made (#459).

Against `origin/main` revision `bdedc62d` it classifies 198 distinct imports as 27 implemented, 95 partial and 76 missing, and groups the missing `KERNEL32.dll` names by subsystem. This static CSV census is explicitly not a reproduction of the historical multi-module package preflight counts; no authorized redistributable DLLs were available, none were committed, and no execution claim is made.

Fixtures cover both vector widths against the independent byte-array reference, a deterministic regression separates the halves' bit positions, and the AVX2 CPUID witness moves to the still-refused 256-bit VPBLENDVB. Evidence is local testing on Apple Silicon only; no x86 hardware comparison, independent acceptance or game compatibility is claimed.

- CRT anonymous pipes are kernel objects now, and process creation inherits them (#1040). `_pipe` builds a kernel pipe pair in the machine-wide object table and wraps both ends exactly as the CRT wraps them on Windows, so `_get_osfhandle` answers real handles, `GetFileType` reports FILE_TYPE_PIPE, and `PeekNamedPipe` reports the buffered byte count - failing with ERROR_BROKEN_PIPE once no write can arrive, which in the synchronous process world is as soon as the buffer drains, since no suspended process can write while the reader runs. A `_spawnve` child inherits its parent's descriptor wiring as the CRT hands it down - pipe ends, wrapped handles, aliases and standard streams, though not owned file streams, whose positions are the parent's own - pipe end references count machine-wide in place of the per-process handle tables, and a pipe object dies exactly when its last reference anywhere closes, the write end's last close marking end of stream. A spawned child's exit no longer wipes the machine-wide object table it shares with its parent and siblings. Measured end-to-end on the real busybox binary: shell pipelines complete and the shell continues after them - `echo hello | tr a-z A-Z` prints HELLO, `echo hi | cat; echo done` reaches done, data chains through `cat | cat`, a pipeline redirects into a file and back out, and cp copies file to file through the spawn and pipe stack - where every pipeline previously hung the shell after partial output or failed with bad-descriptor errors on both ends. Stream-level standard input reads follow the redirection too: `fread`, `fgetc` and `_filbuf` on stdin read what descriptor 0 names once it is duplicated onto a pipe or file, as the CRT's stdin is backed by its descriptor - measured: `echo abc | wc -c` counts 4.
- Paging-file-backed memory mappings share their content across the machine now (#1040). `CreateFileMapping` carries one backing byte store per object, a view copies it in at mapping time and out at unmapping, flushing and process spawn, so a child process mapping the handle its parent passes - the numeric handles being machine-wide, as inherited handles are on Windows - reads what the parent wrote. This is the hand-off the busybox win32 shell's fork emulation uses, measured end-to-end on the real binary: the shell re-executes itself, the child reconstitutes from the shared state, runs the command and the parent's `OpenProcess`/`WaitForSingleObject`/`GetExitCodeProcess` chain collects its exit status, so shell command sequencing with correct `$?` propagation works. Views reconcile only at those synchronization points since one process executes at a time, which is exact for spawn-then-wait hand-offs and documented as the limit; writes a finished child never unmapped do not reach the parent.

- XAudio2 source voice creation now accepts the documented 16-byte PCM header at the end of readable guest memory. IEEE float still requires its 18-byte header (#1472).

- `fopen` now allocates the legacy CRT's full 48-byte `_iobuf`, zeroed, instead of 8 bytes: the mingw-w64 CRT real-world binaries link expands `getc`/`putc` as macros that decrement `_cnt` and step `_ptr` inside the object in place, so the first macro use faulted on the unmapped byte past the small allocation and applets reading a file by name (`wc`, `grep`, `sort`, `head`, `od`) died in the CRT exception filter before any read. A zero `_cnt` sends every byte through `_filbuf`/`_flsbuf`, exactly as the unbuffered stream behaves on Windows. Local verification only (public busybox mingw64 binary).
- A 67H address-size override before opcodes E0 through E3 is now refused rather than silently testing the full RCX. In 64-bit mode those opcodes select ECX under the override; Xenora does not model the narrow count, so the decoder fails closed in both engines while JRCXZ and LOOP without the override keep their verified 64-bit answers (#1168).

Local Apple Silicon verification only; no x86 hardware comparison or independent acceptance is claimed.
- File redirections a shell puts in place for a spawned program now reach that program: the C runtime inherits the file-backed descriptors into the child as position snapshots whose final positions write back into the parent when it finishes, and the standard output and error streams write through descriptors 1 and 2 when a redirection rewires them rather than bypassing the descriptor table, so BusyBox constructs such as `ls > f`, `seq 3 | wc -l > out` and `seq 3 | xargs echo` now answer correctly where the redirected output previously leaked into the console capture or never arrived. Local verification only (public busybox mingw64 binary).
- LOOP, LOOPE, LOOPNE and JCXZ now select their count register by the address-size attribute: with the 67H override the count is ECX rather than RCX, superseding the earlier decode-time refusal of the override on those opcodes. A LOOP form decrements ECX alone leaving the upper bits of RCX unchanged, and the test forms read ECX alone, as Intel SDM Vol. 2A states. New known-answer vectors pin the ECX count, the wrap at zero and the preserved upper bits at every engine, and `cpu_addrsize` now verifies the narrow-count branch behavior directly. Local verification only.

### Fixed

- Fixed the intermittent failure of the frame-loop memory-footprint test (#290). Each frame-loop session opened its own Metal command queue. The first command buffer on a queue makes the GPU driver allocate a working set for it (about 45 MiB on an Apple M5 with Metal validation), and the driver frees it asynchronously 10–50 ms after the queue is released, so the process footprint read right after a session ended depended on how far that release had got. Measured immediately after each of 50 destroys, it ranged from 45 to 96 MiB; the unchanged test failed 5 times in 30 runs, with up to 26 MiB of apparent growth. There was no leak: one second after each destroy the footprint was back at the same floor every time. Frame-loop sessions now share one process-wide Metal device and command queue, so the working set is allocated once and kept: the same readings stay within 93–98 MiB across 50 sessions, and the unchanged test passed 30 runs in a row (largest growth 0.31 MiB). The cost is that the process keeps that GPU memory (about 50 MiB with validation, 58 MiB total footprint without) after its first frame loop. A new 50-session test (normal completion, pause and resume, destroy while running) checks the readings stay within 16 MiB; it fails without the fix.
- Stop ignoring `fixtures/pe/trusted-runner.exe`. The runner embeds it with `include_bytes!`, so ignoring the file made a fresh checkout fail to compile.
- Corrected the ARM64 STP pre-index encoder, which had a hardcoded -32-byte immediate and therefore adjusted the host stack by the wrong amount once the translator frame grew to 48 bytes. The wrong frame silently corrupted the caller's stack and caused SIGSEGV in every native translation test. Emitter encodings are now checked against LLVM's assembler, and a test asserts that each translated block opens and closes the same 48-byte frame.
- Translated guest memory faults now stop the block before it commits further architectural effects. A faulting push, call or store leaves guest RSP and registers unchanged, the reported instruction count covers only completed work, and guest RIP identifies the faulting instruction. Previously the block continued after the helper recorded a fault, so later instructions and writes still took effect.
